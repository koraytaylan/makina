# Scope — Plan 0037

> Audit the Ayu theme implementation for visual distinctness, verify all color paths pull from the active theme (not hardcoded), ensure truecolor RGB output on modern terminals, and add theme-aware styling for selection highlights and code blocks so the three Ayu variants render visibly distinct.

## Why this plan

**1. The three Ayu variants render nearly identically instead of being visually distinct.** Plan 0036 delivered the theme abstraction, three Ayu palettes, and palette-switching via command palette, but user reports indicate the three variants (Dark, Mirage, Light) appear nearly the same on screen. The root cause is that not all color-bearing rendering paths have been migrated to pull from the active theme. Specifically: (a) markdown code blocks at `markup.rs:128,133` use hardcoded `Modifier::DIM` and `Modifier::REVERSED` (not theme colors), (b) `render_markdown` has no theme parameter, so its hardcoded modifiers cannot be overridden, (c) accordion section header focused state at `ui.rs:2120–2124` uses `theme.get(Dim)` as background, which may have insufficient contrast with SelectionBg in the light theme, and (d) selection highlighting was moved to theme colors but may not be distinct enough in all variants.

**2. Truecolor (24-bit RGB) output is not verified for modern terminals like Ghostty.** Plan 0036 pins all Ayu colors as `Color::Rgb` (truecolor) values, but the codebase does not verify that ratatui emits true 24-bit escape sequences (`\x1b[38;2;R;G;Bm` and `\x1b[48;2;R;G;Bm`) for these colors on truecolor-capable terminals. Without this verification, there is a risk that ratatui downsample these colors to the 16-color ANSI palette (less distinct) on some terminal backends, defeating the visual distinctness goal. The TestBackend render test at `ui.rs:8923–8958` checks that theme colors reach the Buffer, but does not verify the *escape sequences* emitted to stdout.

**3. Selection highlight and focused accordion-section styling lack comprehensive visual distinctness audits.** Selection highlighting (`selection.rs:136–142`) uses theme colors but the contrast between SelectionBg and Foreground may be marginal in the light theme (both light colors). The accordion section header focused state (`ui.rs:2119–2124`) applies `theme.get(Dim)` as the focused background, which may blend poorly with the default foreground in some variants. There are no visual regression tests or snapshot assertions proving the three variants render with distinct colors for selections/highlights across all widget contexts.

**4. Markdown code blocks use hardcoded modifiers (DIM, REVERSED) instead of theme-aware colors.** Code blocks and inline code at `markup.rs:128–134` use `Modifier::DIM` and `Modifier::REVERSED` without any involvement of the active theme. This means the code block appearance does not change when switching themes — it always uses the terminal's default colors plus modifiers. For visual distinctness, code blocks should use a theme-aware color pair (e.g., a new CodeBlock role with foreground and background, or Info role's colors).

**5. A comprehensive sweep for hardcoded Color:: literals outside tests has not been performed post-migration.** Plan 0036's ARCHITECTURE.md says production `Color::` sites were migrated in ui.rs and ansi.rs, but does not provide an enumeration or verification. A grep to confirm no production hardcoded colors remain (except in test stubs) would provide confidence that all render decisions go through the theme.

Work items in [TASKS.md](TASKS.md) (workstreams 0001–0003):

- **0001 — Theme-Aware Markdown Code Block Styling.** Update `markup.rs::render_markdown` to accept a `Theme` parameter; replace hardcoded `Modifier::DIM` and `Modifier::REVERSED` for code blocks and inline code with theme-based colors from a new `CodeBlock` semantic role (or reuse `Info`). Thread the theme parameter through all callsites in `ui.rs`.
- **0002 — Selection and Focus Highlight Distinctness Audit.** Verify that selection/highlight colors (SelectionBg + Foreground) and accordion focused state (Dim background) have sufficient visual contrast in each of the three Ayu variants. Update the focused accordion-section header styling to use a more distinctive background color (e.g., SelectionBg or a new FocusBg role) instead of Dim, and add visual regression tests that assert the three variants render with distinct highlight cells under TestBackend.
- **0003 — Hardcoded Color Sweep and Truecolor Verification.** Grep ui.rs and ansi.rs for any remaining production hardcoded `Color::` literals outside test blocks; confirm all render-time color decisions go through `theme.get()` or `theme.ansi()`. Verify that ratatui emits truecolor (24-bit RGB) escape sequences for `Color::Rgb` on modern terminals, and add an assertion test confirming cells rendered with `Color::Rgb` do not get downsampled to 16-color ANSI.

## Locked decisions

- **CodeBlock styling uses theme colors, not terminal-default modifiers.** Markdown code blocks and inline code will use `theme.get(ThemeRole::CodeBlock)` as foreground and `theme.get(ThemeRole::Background)` as background, retaining `Modifier::DIM` for subtle emphasis. This ensures code blocks respond to theme switches and render distinctly in each Ayu variant. The alternative (keeping `Modifier::REVERSED` for maximum contrast) would invert colors unconditionally, making code blocks look jarring in light themes; theme-aware colors are more harmonious. This decision holds as long as `CodeBlock` role values are chosen to provide good contrast in all three variants (verified by value-pinning tests).
- **FocusBg role is separate from SelectionBg for accordion focus states.** While both represent "active highlight" concepts, accordion section focus (keyboard/mouse navigation) and text selection (mouse drag) are distinct user affordances. Using separate roles (`FocusBg` for keyboard focus, `SelectionBg` for text drag) allows independent fine-tuning per variant and clearer semantic intent in the render code. If future requirements merge the concepts, the two roles can be unified. This decision holds as long as both roles are value-pinned and tested for distinctness per variant.
- **Truecolor verification focuses on application-layer Buffer representation, not terminal escape sequences.** The test `test_render_produces_truecolor_cells_not_ansi16` verifies that the ratatui Buffer (the intermediate rendering artifact) contains `Color::Rgb` values, not `Color::Indexed`. It does not and cannot verify the *terminal output* (ANSI escape sequences) without spawning a real PTY and parsing stdout, which is out of scope for the test suite. Ratatui's crossterm backend automatically detects terminal capability and emits 24-bit sequences (`\x1b[38;2;R;G;Bm`) on capable terminals (Ghostty, iTerm2, modern terminals); this is ratatui's responsibility, not Makina's. This decision holds as long as the app defines colors as `Color::Rgb` and relies on ratatui/crossterm for proper terminal-specific output.
- **The grep audit is a manual human review; no automated linting is introduced to prevent future hardcoded colors.** A clippy lint or custom proc-macro could theoretically enforce "no `Color::` literals in production code," but such tooling is out of scope for this plan. Instead, the post-implementation grep audit serves as a one-time verification, and the value-pinning/buffer tests serve as regression guards for future changes. Code review practices and the test suite are the guardrails. This decision holds; if future plans introduce a lint-based enforcement, this audit approach can be retired.

## Out of scope

- User-defined custom themes or theme-import mechanisms. Plan 0036 delivered a hardened abstraction for future user-defined themes, but allowing users to upload/import custom themes is a separate feature (file validation, color parsing, serialization, UI for theme management). This plan focuses on fixing and auditing the built-in Ayu themes, not extending the system to user-defined ones.
- Terminal capability auto-detection or fallback to 16-color mode on legacy terminals. Ratatui and crossterm handle terminal capability detection and color downsampling transparently. This plan assumes modern terminals (Ghostty, iTerm2, etc.) support truecolor and verifies the app emits `Color::Rgb` values; actual fallback behavior is ratatui's responsibility, not Makina's.
- Language-specific syntax highlighting for code blocks in Markdown. Plan 0020 deferred syntax highlighting; plan 0035 (task entries) reused the same Markdown renderer without adding language detection. This plan improves code-block styling via theme colors but does not introduce tokenization or language-specific highlighting.
- Animated theme transitions or smooth color interpolation. Theme switching via command palette is instant (no animation). Future visual polish might include fade transitions; this is out of scope.
- Per-widget theme overrides or local style adjustments. The theme system provides a global palette; individual widgets inherit from it. Widgets cannot currently override a specific role's color for local emphasis (e.g., "make this button brighter"). Such granularity is out of scope; widgets use theme roles as-is.
- Adding new Ayu variants (e.g., Ayu Sunrise or other community variants). The plan focuses on auditing and fixing the three existing Ayu variants (Dark, Mirage, Light) from the canonical ayu-colors spec. Adding new variants is a future enhancement.
