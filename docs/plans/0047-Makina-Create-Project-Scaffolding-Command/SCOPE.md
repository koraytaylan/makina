# Scope — Plan 0047

> Give Makina a headless `makina create <path> [--template todo]` subcommand that bootstraps a brand-new, immediately-runnable experiment project in any folder OUTSIDE the makina repo — reusing the shipped `folder_init` bootstrap and 0046 CLI seams — so an outside developer's first run is `makina create ~/tmp/todo && cd ~/tmp/todo && makina` with zero risk of clobbering the makina working tree.

## Why this plan

**1. The scaffolder has nothing to scaffold — there is no embeddable sample project.** `crates/makina/src/templates/` holds only `plans_readme.md` (the sole file in the directory), and `folder_init::initialize_folder` embeds exactly that one template via `include_str!("templates/plans_readme.md")` (`crates/makina/src/folder_init.rs:75`) to write `docs/plans/README.md` — so a fresh folder gets a git repo and an authoring guide but no runnable code, no committed `.makina/config.toml`, and no example plan. A `create` command needs a complete, immediately-runnable `todo` project to stamp out, and none is committed.

**2. `initialize_folder` exists but nothing creates a project OUTSIDE the makina repo, which is exactly how the workspace got clobbered.** `initialize_folder` (`crates/makina/src/folder_init.rs:16`) is only ever driven by the in-TUI `AppEvent::InitializeFolderSelected` handler (`crates/makina/src/event.rs:425`) against a user-picked folder; there is no headless caller, no conflict rule that refuses a non-empty directory, and no seam that stamps a full project. The incident commit `934d1b3` (`fix: restore makina workspace root clobbered by plan-0001 merge`) is the concrete damage this prevents by design: throwaway experiments must live in their own folder OUTSIDE the repo, created safely, never inside the makina working tree.

**3. The CLI parser has no `create` subcommand, so `makina create …` is rejected as an unknown flag.** `parse_args` (`crates/makina/src/cli.rs:16`) matches only `-h/--help`, `-V/--version`, and `--doctor`, and returns `CliAction::Unknown(other)` for anything else; the `main` dispatch (`crates/makina/src/main.rs:68`) routes `Unknown` to `eprintln!` + `std::process::exit(2)` (`main.rs:80-82`). There is no `Create` variant, no `--template` handling, and no headless arm that scaffolds and exits before the TUI startup at `main.rs:84`.

**4. No test exercises project scaffolding, though the hermetic git helpers to do so already ship.** The scaffold seam does not exist, so nothing asserts the git structure, the sample `.makina/config.toml`, or that the stamped plan triad parses; meanwhile `makina_core::test_support` already exposes `run_git` (`crates/makina-core/src/test_support.rs:10`), `setup_temp_repo` (`test_support.rs:28`), and `init_git_repo_with_identity` (`test_support.rs:37`), and the `makina` crate already dev-depends on `makina-core` with the `test-support` feature — an end-to-end scaffold test can be added with no new dependency.

**5. The README's only "experiment safely" guidance is a throwaway clone, not a zero-risk create path.** The Caution section (`README.md:156`) tells first-timers to `git clone /path/to/repo /tmp/repo-trial` (`README.md:165`) before the Run section (`README.md:168`) — a clone of the makina repo itself, still adjacent to it. There is no `makina create ~/somewhere/todo --template todo` recommendation giving a brand-new project in an unrelated folder, which is the safest possible first run.

## Locked decisions

- **Template files are stored under neutral names, not their real destination names.** The `todo` template lives under `crates/makina/src/templates/todo/` with neutral file names (`cargo_toml`, `main_rs`, `makina_config_toml`, `plan_*_md`), each `include_str!`-embedded and written to its real destination by `scaffold_project`. This mirrors the shipped `templates/plans_readme.md`→`docs/plans/README.md` rename pattern (`folder_init.rs:75`) and guarantees no literal `Cargo.toml` sits inside the `makina` crate's `src/` tree — which could otherwise confuse `cargo package`/workspace resolution (root uses `members = ["crates/*"]`). Revisit only if a future templating mechanism needs on-disk fidelity of the destination names.
- **`initialize_folder` stays in the `makina` binary crate; no relocation to makina-core.** `folder_init::initialize_folder` (`crates/makina/src/folder_init.rs:16`), its only existing caller (`event.rs:425`), and the new `scaffold`/`create` dispatch all live in the `makina` crate, so `scaffold_project` calls it in-crate with no layering change. Relocating it to `makina-core` would be churn for no benefit today. Revisit if a non-`makina` crate ever needs to bootstrap folders.
- **Scaffolded initial content lands on `develop`, not `main`.** `initialize_folder` leaves an empty bootstrap commit on `main` and branches `develop` off it. `scaffold_project` checks out `develop`, writes the template files, and commits them there — because `develop` is the base branch Makina drives (the template `.makina/config.toml` sets `base_branch = "develop"`) and the auto-discovery in `main.rs` operates on the base branch. `main` intentionally stays at the empty bootstrap commit. Revisit if the template config ever ships a non-`develop` base branch.
- **Only the `todo` template exists; the template set is a closed `AVAILABLE_TEMPLATES` const.** `--template` defaults to and only accepts `todo`; `AVAILABLE_TEMPLATES: &[&str] = &["todo"]` is the single source of truth checked in both `parse_args` (user-facing error listing available templates) and defensively in `scaffold_project`. An unknown template is a `CreateError` that lists `AVAILABLE_TEMPLATES` and exits 2. Adding templates later means appending to the const and adding a `templates/<name>/` directory plus its file map.
- **The scaffolded project's own compile is an `#[ignore]`d test; structural assertions are the everyday gate.** Compiling the stamped `todo` crate (`cargo test` inside the temp project) is slow, so `scaffolded_todo_project_passes_its_own_gates` is `#[ignore]`d and run explicitly, while `scaffold_creates_runnable_todo_project` asserts the git structure, the sample config, and the plan triad structurally on every `cargo test`. Revisit if CI gains a cheap, isolated way to compile scaffolded output routinely.

## Out of scope

- Adopting `clap` or any argument-parsing crate for the `create` subcommand. The hand-rolled parser in `cli.rs` (plan 0046) already serves the flag surface; `create <path> [--template <name>]` extends it with a small pure `parse_create`, adding zero dependency weight and staying trivially unit-testable.
- Additional templates beyond `todo` (e.g. library, web, multi-crate). The zero-risk first-run path needs exactly one immediately-runnable example. The template set is a closed const that later plans can extend without reworking the command.
- An interactive/TUI 'new project' wizard. `makina create` is deliberately headless (scaffold and exit before any TUI init) so it is scriptable and safe for a first run; an in-TUI flow is a separate concern.
- Changing `folder_init::initialize_folder`'s existing behavior or its in-TUI caller (`event.rs:425`). `scaffold_project` reuses `initialize_folder` unchanged; altering the shared bootstrap or the TUI path risks regressing plan 0043's multi-folder init and is unnecessary for scaffolding.
- Publishing the scaffolded `todo` crate as a workspace member or CI-built artifact. The template is stamped into an external folder at runtime; it is never a member of the makina workspace and is not built by makina's own CI.
