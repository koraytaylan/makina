# Scope — Plan 0041

> Extract and consolidate code-hygiene improvements identified in the glm-5.2 review: shared helper extraction, atomic run.json writes, stale doc fixes, dead-code-allow cleanup, stub-event resolution, and deduped validation.

## Why this plan

**1. Developer/Reviewer stream-drain duplication creates maintenance hazard.** The stream-drain loop in `reviewer.rs:259–386` (idle-watchdog + side-channel forwarding + `RoleTurnMetrics` emission) is near-identical to `developer.rs:289–417`, approximately 130 lines duplicated across the two roles. Any bug fix or feature addition to one path must be applied to the other; the two sites can drift, and a junior engineer reading the code encounters unexplained repetition. A shared `drain_agent_turn(session, events, role, ...)` helper would centralize the logic, improve readability, and eliminate the sync burden.

**2. `combine_output` is defined identically in two places.** `combine_output` appears at `gate.rs:241` and `merge.rs:482` with identical bodies and identical unit tests. The duplication is low-impact (small, stable function), but violates DRY; moving it to a shared internal utility module and importing it in both places (or adding it to a shared helper crate) would cut the boilerplate.

**3. `run.json` persistence is not atomic; `persist_graph` is.** The graph-persistence code (`persist.rs:173–205`) writes atomically: write to temp file, rename onto canonical path (same filesystem → atomic). The run-metadata code (`run_metadata.rs:173–185`) does a single `tokio::fs::write` directly to the destination; a crash mid-write could leave a truncated `run.json`. Although `run.json` is a historical record (not the source of truth), the inconsistency with the graph-persistence discipline is worth fixing for coherence and safety.

**4. State machine doc comments are stale.** The test-module doc and in-test comments in `state_machine.rs` (`:325`, `:327–328`, `:335–336`, `:346`, `:407`, `:412–413`) still cite "19 legal / 65 illegal / 84 pairs" (7×12), but the addition of `RetryRequested` and `DependencyReset` edges brought the actual counts to 21 legal / 77 illegal / 98 pairs (7×14). (The module-level doc at `:1–70` carries no counts and needs no change.) The code and the test assertions are correct; the documentation was not updated. A reader comparing the docs to the test assertions finds a mismatch.

**5. `run_metadata.rs` doc comment is stale.** Lines 69–71 claim `WorktreeManager::worktree_path` "still returns the pre-relocation path," but it does not — it delegates to `paths::worktree` which returns the relocated off-repo path. The comment predates plan 0029 (which implemented the relocation).

**6. `#[allow(dead_code)]` permits sit on symbols that no longer need them.** Three are used in production code, so the allows are pure stale cruft: `is_plan_convention_dir` (`orchestrator.rs:190`, used at `:1312`); `format_tasks_section` (`ui.rs:2170`, used at `:1999`); `accordion_section_order` (`app.rs:1771`, used at `:1802`/`1855`/`1872`). The fourth, `PlaceholderApi::empty` (`crates/makina/src/placeholder.rs:73`, allow at `:72`, in the TUI crate — NOT makina-core), is test-only: its only callers live in `#[cfg(test)]` modules, so the allow cannot simply be deleted (the non-test lib build would flag `dead_code`). The three production allows are removed; `empty()` is either kept allowed or `#[cfg(test)]`-gated.

**7. `SettingsCommit` validation is duplicated in two places.** `App::update` (the `SettingsCommit` arm, `app.rs:2856–2963`, ~108 lines) validates settings fields, and `event::commit_settings` (`event.rs:613`) does the same validation. Both must stay in sync; a change to validation rules (e.g., tightening a cap, adding a field) requires updates in both places, creating a maintenance hazard. The two differ only in error-surfacing: `commit_settings` early-returns `Some(reason)`, while `App::update` accumulates into `settings.error` with a `has_error` short-circuit and keeps the modal open. The validation logic should be shared, with each call site preserving its own error-surfacing.

**8. A stub retry event shadows the real retry, the palette dispatch path has a structural gap, and a dead discover-stub arm lingers.** The real retry and discovery paths are implemented ONLY in `resolve_io`: `AppEvent::RetryFocused` (`event.rs:346` → `retry_focused`, `event.rs:1028`, which calls `api.execute(Command::RetryTask/RetryFailedTasks)`) and `AppEvent::DiscoverProject` (`event.rs:414` → `discover_project`). `App::update(RetryFocused)` is a deliberate NO-OP (`app.rs:2464`). A separate stub variant `AppEvent::RetryFocusedTask` (`app.rs:900`) also exists, and the command palette wires "Retry failed task" to that stub — not to the real `RetryFocused` — so the palette's retry action hits the `App::update` arm at `app.rs:2967` and emits "retry not yet available (plan 0017)". (The glm-5.2 review item 22's claim that the palette is wired to the *real* events is factually wrong; the palette is wired to the stub at `app.rs:482`.) CRITICAL: merely repointing the palette action at `RetryFocused` does NOT fix retry — it turns the stub message into a silent no-op. The palette dispatch path is `CommandPaletteExecute` → `resolve_io` EXTRACTS the action's event and returns it (`event.rs:389–409`) → the loop calls `app.update(extractedEvent)` DIRECTLY (`event.rs:224–226`) with NO second `resolve_io` pass — so a palette-dispatched `RetryFocused` reaches only the no-op `App::update` arm. (The same gap silently affects the palette's other IO-backed actions.) The fix must RE-DISPATCH palette IO events through `resolve_io` (e.g. send the extracted event back over `background_tx`, which the loop reprocesses through `resolve_io` at `event.rs:156`/`224`) so retry reaches `retry_focused`. Separately, the single `DiscoverProject` variant has a dead `App::update` arm at `app.rs:2971` that `resolve_io` never reaches. The cleanup must re-dispatch palette IO events through `resolve_io`, repoint the palette's retry action at the real `RetryFocused`, delete the now-orphaned `RetryFocusedTask` stub variant + its `App::update` arm, and delete the unreachable `DiscoverProject` stub arm in `App::update` while keeping the `DiscoverProject` variant.

## Locked decisions

- **`drain_agent_turn` returns accumulated output and usage, with a shared error type.** The extracted `drain_agent_turn` helper returns `Result<(String, Option<api::UsageStats>), DrainError>` — the accumulated response text and the turn's usage (the `usage` field of `ResponseEvent::TurnComplete`, `backend.rs:245`). Because the Developer and Reviewer actors surface DISTINCT error enums (`DeveloperError` at `developer.rs:70`, `ReviewerError` at `reviewer.rs:67`), the helper returns a shared `DrainError` (or is generic over the role error) that each actor maps into its own enum at the call site. (The type names `DeterminismError` / `TokenUsage` from early drafts do not exist in the crate.) No change to the orchestration API or supervisor contract.
- **`combine_output` is moved to a shared internal module, not pub.** The `combine_output` function is `pub(crate)` in its new shared module; it is not part of the public API surface. Both gate.rs and merge.rs import it privately. Tests for the function stay with the helper module.
- **`run.json` temp file uses process ID and a sequence counter for uniqueness.** Following the persist.rs pattern, temp files are named `run.json.tmp.{pid}.{seq}` where `seq` is a process-global atomic counter. This ensures no collisions across concurrent processes or concurrent calls within a process, and cleanup is best-effort (a crashed write leaves a temp file; cleanup on next run or explicit prune is acceptable).
- **`SettingsCommit` validation is extracted to a shared module.** Validation logic is centralized in `crates/makina/src/settings_validation.rs`, returning a `Result<SettingsValidation, String>`. Both `App::update` and `event::commit_settings` call this shared validator, ensuring they stay synchronized. Any future changes to validation rules are made in one place.
- **Palette IO events are re-dispatched through `resolve_io`; the retry action is repointed at the real event; only the orphaned stub is removed.** Because palette-dispatched events skip the `resolve_io` pass (`CommandPaletteExecute` returns the extracted event straight to `App::update`), the `CommandPaletteExecute` arm is changed to re-dispatch IO-backed events through `resolve_io` (send the extracted event over `background_tx`; the loop reprocesses it through `resolve_io`). The palette's "Retry failed task" action is rewired from the stub `AppEvent::RetryFocusedTask` to the real `AppEvent::RetryFocused` (handled in `resolve_io` at `event.rs:346` → `retry_focused`, which issues `Command::RetryTask`/`RetryFailedTasks`), so the action actually retries rather than hitting the deliberate `App::update(RetryFocused)` no-op (`app.rs:2464`). The now-unused `RetryFocusedTask` variant and its `App::update` "not yet available" arm are then deleted. The `DiscoverProject` variant is KEPT — it is the real, palette-wired discovery event (`resolve_io` at `event.rs:414` runs `discover_project`); only its dead, unreachable `App::update` "not yet available" arm is deleted. No new `Retry`/`Discover` variants are introduced.

## Out of scope

- Implementing a comprehensive cross-crate audit of dead code. Plan 0041 targets four specific stale pragmas cited in the review; a full codebase audit is out of scope.
- Refactoring the `SettingsCommit` event dispatch or handlers beyond deduplication. Only the validation logic is deduplicated; the event handling and application of settings remains in place.
- Implementing keybinding configuration or event-dispatch customization. Stub-event removal is cleanup; no new configurability is added.
- Adding new runtime atomicity guarantees or crash-recovery enhancements. Making run.json atomic is a consistency fix to match persist_graph; no new recovery logic is added.
