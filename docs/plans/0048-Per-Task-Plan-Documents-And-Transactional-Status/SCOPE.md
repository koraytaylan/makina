# Scope — Plan 0048

> Replace Makina's monolithic `TASKS.md` contract with typed per-task plan documents, then make every durable status transition a coordinator-owned, Git-backed update of the task file, the plan status, and the root roll-up.

## Why this plan

Makina can schedule tasks today, but the plan authoring format and the execution model have drifted into a split contract. Discovery, previews, ingestion, run identity, runtime artifacts, generation, and the TUI all treat `TASKS.md` differently. Status is held mostly in `.makina/tasks/*.json`, while the human plan documents do not move with the work. That makes a plan hard to review before execution and hard to trust afterward.

This is an intentional clean break. Makina has not been released and has no user base, so preserving the old executable format would add ambiguity without protecting anyone. Historical `TASKS.md` plans remain readable repository history, but they are not executable inputs after this plan. Provenance: authored against `develop` @ `d428def`; symbol names below are anchors and line numbers are deliberately omitted.

1. **`TASKS.md` is both a filename and an accidental API identity.** `orchestrator.rs` derives run slugs from it, discovers it recursively, parses a preview from it, and passes it through `OpenRun`; `api.rs`, `run_metadata.rs`, `project_api.rs`, `event.rs`, `app.rs`, and `ui.rs` repeat the same file identity. A plan directory must become the single identity instead.
2. **There are multiple interpretations of one plan.** `parse_plan_tasks`, `TaskListInterpreter`, `StructuredTextInterpreter`, `ModelInterpreter`, and the normalizer do not share one typed document loader. A plan can therefore preview one way, execute another way, and replay from cached JSON without rereading its source.
3. **Runtime artifacts have become a second source of truth.** `CoreApi::open_run` prefers `.makina/tasks/{slug}.json` when it exists. Edits to dependencies, gates, footprints, or task instructions can be silently ignored, and a stale runtime `Done` can survive without matching Git evidence.
4. **Authored task semantics are missing from the runtime model.** There is no durable representation of `workstream`, `kind`, `gated`, `touches`, authored status, or the merge commit recorded for a task. Collision inference relies primarily on prose instead of an explicit write footprint.
5. **No component owns durable status updates.** The task frontmatter, plan `STATUS.md`, and root `docs/plans/STATUS.md` are not updated by execution. Letting parallel developer agents edit those shared files would create avoidable merge conflicts and could record a task as done before Git has accepted it.
6. **Two runs in one repository can race even if each run serializes its own merges.** `DriverContext::merge_lock` is per run. It cannot protect the shared plan branch, root roll-up, or plan-status documents from a second active run in the same Git common directory.
7. **Authoring and scaffolding still emit the old contract.** The normalizer, model generation path, project templates, specs, `.claude` skills, and `.claude/workflows` all teach or write `TASKS.md`. The cutover is incomplete until every live producer and consumer speaks the same format.
8. **Integration currently mutates the operator checkout destructively.** The plan branch is checked out at `repo_root`; task/final merges and Stage operate there, conflict cleanup can reset/clean it, stale worktrees are force-removed, and `ResetRun` deletes plan refs. Transactional status and retained provenance require a Makina-owned integration workspace first.
9. **Task status alone cannot describe plan integration.** All tasks can be done while a plan is awaiting final integration, finalization-pending, conflicted, staged, manually retained, or complete. `STATUS.md` needs typed plan-level integration evidence in addition to derived task counts.

## In scope

- **0001 — Typed plan documents and validation.** Bootstrap this one self-format-changing plan through the agent workflow, then introduce the only parser and renderer for `SCOPE.md`, `ARCHITECTURE.md`, `STATUS.md`, and `tasks/*.md`; strictly validate frontmatter, filenames, task bodies, workstreams, dependencies, status coherence, containment, and the DAG.
- **0002 — Runtime projection.** Project validated task documents into `TaskGraph`, treat runtime JSON as a checked checkpoint only, and use authored gates and footprints in scheduling.
- **0003 — Plan-directory identity and UI.** Replace every live `TASKS.md` path in the API, discovery, run metadata, project routing, events, application state, and TUI with a canonical plan-directory identity and source-aware status presentation.
- **0004 — Transactional status and Git evidence.** Serialize executing plans per Git repository and process, isolate all integration mutations from the operator checkout, capture implementation commit identities and trailers, and make the integration coordinator land task/status bookkeeping as a recoverable two-phase operation. Reconcile source, Git, and runtime state on reset/resume and across final merge modes.
- **0005 — Authoring cutover.** Generate and register complete task bundles under the repository lease, port the repository's plan skills and workflows, publish the new authoring/scaffold contract, and remove all live code, tests, templates, and normative documentation that can create or execute `TASKS.md`.

## Locked decisions

- **`tasks/` is both the format discriminator and the sole executable task format.** A new-format candidate is a directory containing `tasks/`; it is executable only with `SCOPE.md`, `ARCHITECTURE.md`, `STATUS.md`, and a non-empty set of valid `tasks/*.md` documents. Directories without `tasks/`—including historical SCOPE/ARCHITECTURE/STATUS/`TASKS.md` combinations—are inert. There is no `TASKS.md` fallback, compatibility flag, automatic migration, or mixed-format plan.
- **Plan 0048 has one explicit bootstrap task and one authoring prerequisite.** Before execution, this authored closed bundle must be present in the exact target-base commit; working-tree-only plan bytes are `AwaitingCommit` and cannot bootstrap. The root row may already match, but Phase R derives and overlays it atomically rather than trusting working-tree bytes. An external coordinating agent then acquires an exclusive Unix `flock(2)` on the persistent, never-unlinked `<git-common-dir>/makina.repository.lock`; validates that committed source; and creates distinct Phase R on `plan/{slug}` with source/executable digests, validation-base, and expected-old ref evidence. Only then does it claim and land `bootstrap-per-task-plan-execution` as footprint-checked Phase A/B without invoking the old destructive workflow. The installed per-task executor executes the remaining DAG under that cross-process lease, enforcing authored changed-path containment at review and immediately before every Phase A. It fails closed when the lease, committed source, R, or exact footprint check is unavailable. After task 0502 reaches Phase B, the bootstrap coordinator makes a durable self-upgrade handoff: it stops scheduling, closes and reaps the Python holder, launches one long-lived Rust contract session, and lets that session reacquire the same canonical lock before rereading/reconciling R/A/B and continuing. A contender may win that unavoidable close/reacquire gap; in that case the upgrade waits visibly and performs no mutation without the lease. The external bootstrap recovery copy, exact-B binary/build evidence, and endpoint data remain through verified C/stable Close (or retained Stage/Manual), so a post-Ready crash can still resume. No operator-checkout mutation, temporary `TASKS.md`, or manual user bookkeeping is permitted.
- **The plan directory is the stable source identity.** APIs and persisted metadata carry the canonical repository-relative plan directory, never `TASKS.md`, `tasks/`, or a synthetic file path. Task IDs are unique within that plan. Branches, worktrees, runtime paths, and run IDs remain plan-qualified so equal task IDs in different plans cannot collide.
- **One typed loader serves every live consumer.** Discovery, validation, execution, generation, preview rendering, status mutation, resume, and the final `.claude` workflows all use the same Rust `PlanDocument`/`TaskDocument` implementation. Agent workflows delegate through one versioned, long-lived headless plan-contract session and retain only orchestration/scheduling logic; they do not carry another YAML/Markdown renderer, diff matcher, or status/Git writer. The session owns the repository lease across agent work and all coordinator mutations until a stable final/retained state. The minimal bootstrap reader is the sole temporary live exception; after self-upgrade it remains only as an inert external recovery copy until the post-C cleanup gate.
- **Plan numbers occupy one repository-wide namespace.** A new-format candidate is invalid when its numeric prefix matches any other numbered plan directory, including an inert historical directory, or any verified Phase-R registration ref, including an R-only generated plan. Historical↔historical collisions remain untouched and inert; generation chooses from the union of numbered directories and registered refs, and root rows continue to key by the globally reserved number.
- **Frontmatter is durable source; JSON is a checkpoint.** Makina always reloads and validates the plan documents when opening or resuming a run. Runtime JSON may restore volatile scheduler state only when the plan identity and executable-field digest match. Bookkeeping-only changes to `status`, `merged_as`, `STATUS.md`, or the root roll-up do not invalidate the digest.
- **Runtime state is always outside the repository.** Checkpoints move to a plan-qualified path below Makina's external per-project state root alongside runs/worktrees. The resolver is fallible and rejects an unavailable user-state root or any result inside the repository; it never falls back to `repo_root/.makina`. Repository-local `.makina` contains committed artifacts only.
- **Task frontmatter is strict and closed.** Required keys are exactly `id`, `title`, `workstream`, `kind`, `depends_on`, `gated`, `touches`, `status`, and `merged_as`. Unknown or duplicate keys, aliases, tags, merge keys, multiple YAML documents, unsafe paths, invalid enums, and resource-limit violations fail validation. `merged_as: ""` has an explicit empty-string↔`None` serde codec; non-empty values must match the repository's reported Git object format (SHA-1 or SHA-256). Add maintained pure-Rust `serde-saphyr` at `0.0.29`; preserve the repository's Rust 1.85 floor and verify it in the dependency task.
- **Filename and body are part of the contract.** Files are named `{workstream-number}{task-number}-{id}.md`, such as `0404-commit-status-with-task-landing.md`; workstreams/sequences are bounded to `0001..0099`/`01..99`, prefix pair `NN` maps to workstream `00NN`, `id` matches the suffix, the H1 matches `title`, and the body contains context, ordered `Steps`, and a final `Done when` criterion.
- **Authored and runtime states stay distinct.** Durable task status is `planned`, `in-progress`, `done`, `blocked`, or `dropped`. Runtime scheduler states remain implementation detail. `gated: true` tasks are visible but never dispatched; the lease-bound coordinator can explicitly `Ungate` a planned gated task or `Drop { reason }` work with no live/unlanded evidence, committing task/Exceptions/root changes before rebuilding runtime state. Before any claim/run/disposition evidence, a committed author edit may replace R through the verified R2 path; the first such execution evidence freezes dependencies/instructions. Thereafter a dependent of dropped work stays blocked and must also be dropped or moved to a new plan. `done` requires valid Git evidence; a stale `in-progress` without a live driver is reconciled before scheduling.
- **`touches` is an enforced expected write footprint.** Its portable grammar is literal paths, single-segment `*`, and terminal `/**`; paths are contained and become the primary collision input. Review and Phase A both reject changed paths outside the footprint. Textual inference may add conservative warnings/edges but cannot contradict an explicit overlap. `.git` and ordinary `.makina` runtime paths are forbidden. Exact `.makina/config.toml` is a typed tracked-config exception: registration must prove an ordinary blob in the immutable validation base and both diff checkpoints allow only status `M` while it remains an ordinary file. Any other exact `.makina` artifact may be deleted only by a `kind: chore` task with the same tracked-blob provenance and status exactly `D`. Addition, rename/copy, type change, unmerged state, submodule change, config deletion, and artifact modification all fail. Provenance remains usable after an allowed deletion.
- **The supervisor/integration coordinator owns status files.** Developer, reviewer, and fixer agents report outcomes but do not edit the active plan's `tasks/*.md`, its `STATUS.md`, or `docs/plans/STATUS.md`. The coordinator commits `in-progress` at claim, `done` plus `merged_as` after a successful task landing, `blocked` on a durable terminal blocker, and `planned` when cancelled/requeued without a blocker. Every transition regenerates plan progress and the root row under one repository lease.
- **All coordinator Git mutations are isolated.** Registration/source-import Phase R, claim/status commits, task landing phases A/B, final phases P/F/C, conflicts, and Stage run in a create-only, run-qualified Makina integration worktree beneath the existing off-repository per-project state root. They never switch, stage, reset, clean, or merge in the operator checkout. Dirty/divergent task or integration worktrees are recovery evidence and are never force-removed.
- **A checked-out base ref is never advanced behind its worktree.** P may be prepared in a detached Makina workspace because it verifies but does not move the target base. Before F/C, Makina inspects every registered worktree. If the target base branch is checked out anywhere outside a Makina-owned clean finalization workspace, the plan remains `finalization-pending` (or `awaiting-integration` before P) and explains how to release/finalize it; CAS never moves that branch out from under the operator index/worktree.
- **A task landing has two recoverable Git phases.** Phase A squash-merges the task work into `plan/{slug}` and records its full commit OID. Phase B writes and validates task frontmatter, plan status, and root roll-up, then creates a separately evidenced bookkeeping commit. Runtime state becomes `Done` and the task worktree may be removed only after Phase B and a clean/accounted-worktree check. If Phase B fails, Phase A remains intact, the task stays non-done with its branch/worktree retained, and resume completes bookkeeping from Git evidence rather than destructively rewinding the plan branch.
- **`merged_as` records implementation evidence.** It is the full repository-format OID produced by Phase A on the plan integration branch, not the task-branch tip, a short display SHA, the bookkeeping commit, or the final base-branch commit. Registration R carries plan/source/digest/base trailers; task landing commits carry `Makina-Plan`, `Makina-Task`, and `Makina-Run`; B/P/F/C carry phase/linkage trailers. UI may abbreviate the OID. Run identity is verified when durable run metadata exists, while plan/task identity plus expected first-parent lineage remains sufficient after checkpoint loss.
- **Git evidence is operational, not tamper-resistant.** Every shared ref update uses expected-old-OID compare-and-swap and every phase is verified from commits/trailers, but an unsandboxed worker that can reach the Git common directory can attempt forgery. The later sandbox plan must make the common directory and coordinator-owned status paths read-only/unavailable to worker processes while coordinator Git runs outside the sandbox.
- **`STATUS.md` carries typed plan integration state without self-reference.** Task counts are derived from frontmatter, while `planned`, `assembling`, `awaiting-integration`, `finalization-pending`, `integration-blocked`, and `complete` plus base/final-integration evidence live in fixed STATUS anchors. Phase P commits pending state before F, and Phase C can therefore store the known F OID; STATUS never stores C's own OID. C is identified by exact completion trailers/history and is written to runtime metadata only after it exists. Blocked/dropped task reasons live in the coordinator-owned Exceptions section. A root Tasks cell is `done/total` normally and `done + dropped / total` when drops exist, so a complete plan never presents an unexplained shortfall.
- **Live status follows the plan integration ref.** While a plan is active, blocked, staged, awaiting manual integration, or prepared but not yet integrated, its authoritative task/status documents live on the retained `plan/{slug}` ref and the TUI reads that view. The base checkout's root board represents the last landed repository state. Every final mode creates evidence-preserving Phase P without rebasing/replacing R/A/B/disposition history; Squash/Merge proceed automatically when possible, Stage retains an exact private index for explicit approval, and Manual exposes an exact prepared-tree recipe. Phase F integrates that tree and Phase C writes complete plus F evidence; interruption after P or F resumes without repeating or rewriting an earlier phase. `Stage` and `Manual` remain non-complete until their typed finalization action reaches C.
- **Successful and recovery plan refs are retained for provenance.** `MergeCommit` preserves task implementation ancestry directly. A final squash commit includes plan/run/task provenance trailers and the retained plan ref keeps every `merged_as` OID reachable. `ResetRun` never deletes durable landing evidence; it rejects dirty ambiguity or archives the old attempt under a run-qualified recovery ref before starting a new one.
- **Only one plan executes per Git common directory across Makina processes.** Plans may be discovered, opened, and queued concurrently, but a registry injected from the application composition root plus the canonical `<git-common-dir>/makina.repository.lock` is held from the pre-start reread through a stable final/retained state. On Unix every implementation uses an exclusive whole-file `flock(2)` on the same persistent inode (open without truncation; unlock by closing; never unlink); unsupported bootstrap platforms fail closed. Later finalization of any prepared mode reacquires the lease and, if base advanced, requires a new evidence-preserving P2 against the current base/root roll-up without rewriting prior landing OIDs; Stage/Manual additionally preserve the exact inspected workspace/recipe. Conflicts or unexpected ref movement fail closed.
- **Registration requires durable source and creates Phase R.** A working-tree-only hand-authored bundle is `AwaitingCommit`, not executable; `RegisterPlan` accepts only an exact plan snapshot present in the current target-base commit, derives its row, binds validation provenance in a private workspace, and creates/CASes Phase R on `plan/{slug}`. Product generation may render outside the checkout and publish the whole bundle/root row directly as R under the same lease. Start claims only from evidenced R, never from operator bytes. This keeps authoring review separate from automatic status updates without requiring manual status edits, and prevents untracked generated paths from colliding with later base checkout/finalization.
- **Historical plans are not bulk-rewritten.** Existing completed plan documents remain as historical evidence. Only live contracts, examples, scaffolds, and tests change. The first executable example of the new format is this plan itself.

## Out of scope

- Backward-compatible execution or migration of historical `TASKS.md` plans.
- Distributed or multi-host repository locking beyond the local Git common-directory advisory lease.
- Bubblewrap integration, platform sandbox backends, or creating a `makina-sandbox` crate; those deserve the next focused plan after this plan format can express them.
- Remote push policy, long-term pruning/export of retained recovery/plan refs, or a hosted provenance database; creating mandatory recovery refs during reset is in scope.
- A general rewrite of task prompting, agent selection, review policy, or model quality.
- Editing the content of completed historical plans merely to make them validate under the new format.
