## 0. Executive summary

Makina is a substantial and thoughtfully engineered MVP, not a scaffold. The
core already contains an explicit task FSM, dependency-aware concurrent
scheduling, task worktrees, deterministic gates, agent review, squash merge,
runtime persistence and recovery, audit logging, provider/role configuration,
and an ACP transport behind a clean backend interface. The TUI exposes that
core through an object-safe API and has unusually broad deterministic coverage.

The current working-tree patch fixes a real regression: a plan stored only in
the multi-folder `plans_by_folder` collection can now be resolved from its tab
or folder-scoped sidebar node, allowing Start to issue `OpenRun` followed by
`StartRun`. Its focused regression test passes.

The patch is nevertheless **not safe to merge or ship as-is**. It routes plans
from arbitrary workspace folders into a single `CoreApi` permanently rooted at
the directory where Makina was launched. A plan from repository B can therefore
be read from B while its artifacts, branches, worktrees, agent edits, gates,
logs, audits, and merge operations target repository A. Folder identity is also
discarded after a plan tab is opened, so duplicate plan slugs are ambiguous.

Two pre-existing core risks are equally important: Start is not exclusive or
single-flight, permitting overlapping schedulers and worktree reclamation; and
concurrent persistence can write an older graph snapshot after a newer one.
The default ACP permission policy is also an audit policy rather than a real
worktree containment boundary: pathless or malformed tool metadata is
auto-approved, and the agent process has no OS sandbox.

### Release assessment

| Area | Assessment | Reason |
|---|---|---|
| Core architecture | Strong | Clear crate/API seams, explicit state machine, extensive tests |
| Multi-folder browsing | Functional | Folders and plans are discovered and rendered |
| Multi-folder execution | Unsafe | One launch-root API executes every folder's plan |
| Run lifecycle | Unsafe under repetition | No idempotent open, scheduler generation, or per-plan exclusivity |
| Persistence | Good foundation, unsafe ordering | Atomic rename exists; concurrent last-writer-wins can regress state |
| ACP transport | Capable but incompletely bounded | Permission gateway exists; idle termination and diagnostics need work |
| Permission safety | Not a sandbox | Missing path metadata is allowed and subprocesses are uncontained |
| TUI patch | Correct narrow fix | Mock API and unique slug do not exercise production routing |
| Merge readiness | Blocked | Cross-repository execution and scheduler ownership are release blockers |

## 1. Critical findings

### 1.1 A plan from a non-launch folder executes against the wrong repository

The shipping binary derives one repository root from process CWD
([`main.rs`](../../crates/makina/src/main.rs#L172)), creates one
`WorktreeManager` from it ([`main.rs`](../../crates/makina/src/main.rs#L297)),
and injects that manager into one `CoreApi`
([`main.rs`](../../crates/makina/src/main.rs#L366)). Workspace discovery,
however, accepts arbitrary additional folders.

Start resolves the selected plan to its absolute `TASKS.md` path
([`event.rs`](../../crates/makina/src/event.rs#L804)) and hands that path to the
single API. `CoreApi::open_run` reads the supplied path, but it loads and writes
runtime state under `state.worktree_manager.repo_root`
([`orchestrator.rs`](../../crates/makina-core/src/orchestrator.rs#L1128)). The
scheduler clones that same fixed manager
([`orchestrator.rs`](../../crates/makina-core/src/orchestrator.rs#L1831)), and
task drivers create branches and worktrees through it.

Consequences when Makina is launched in repository A and the user starts a plan
from repository B:

- B's `TASKS.md` is interpreted.
- Runtime artifacts and discovery state are written beneath A.
- Task branches and worktrees are created from A.
- Agents edit worktrees belonging to A.
- Gates execute against A's checkout and configuration.
- Audit and log roots remain A.
- Approved changes merge into A's configured base branch.

This is a destructive project-boundary failure. `OpenRun` needs a canonical,
registered project identity. Project config, worktree manager, persistence,
logging, and audit dependencies must be selected from that identity. A viable
design is either one project-aware API registry or one `CoreApi` per opened
folder. Paths outside registered roots should be rejected.

The new `RecordingApi` regression proves command ordering only; it cannot
detect root routing because it has no repository or worktree behavior.

### 1.2 Start can overlap schedulers and corrupt run ownership

The TUI's open-and-start helper is detached and records no in-flight state
([`event.rs`](../../crates/makina/src/event.rs#L756)). Repeating Start before
the first `RunOpened` update issues another `OpenRun`. Core allocates and
registers a new run on every call, without task-path deduplication
([`orchestrator.rs`](../../crates/makina-core/src/orchestrator.rs#L1184)).

`start_run` also has no status transition guard. It takes any existing handle,
cancels its token, installs a replacement, sets the run to Running, and spawns
a new scheduler ([`orchestrator.rs`](../../crates/makina-core/src/orchestrator.rs#L1716)).
It does not retain a scheduler `JoinHandle` or generation identifier.

This creates two failure modes:

1. Re-starting the same run can leave the old scheduler finalizing after the
   replacement has started, allowing stale finalization to overwrite status or
   clear the replacement handle.
2. Opening the same plan twice creates distinct live runs with the same
   branch/worktree namespace. `WorktreeManager::create` treats a collision as
   stale state and reclaims it, so one live run can remove another's worktree.

Start should be legal only from explicit states, and opening should be
idempotent for canonical `(project, plan)` identity. Core needs one live run per
project+plan, tracked scheduler generations, and joined or generation-checked
finalization. The TUI should also record an open/start operation as in flight.

## 2. High-severity findings

### 2.1 Folder identity is discarded after opening a plan tab

`TabContent::Plan` and `TabContent::PlanTask` store only `plan_slug`; tab
deduplication therefore treats identical slugs in different repositories as
the same tab ([`app.rs`](../../crates/makina/src/app.rs)). Folder activation
starts with `folder_idx` but immediately drops it when constructing the tab.

The working-tree patch's new `plan_entry_by_slug` helper searches
`plans_by_folder.values()` and takes the first matching slug. Because the
collection is a `HashMap`, the selected project is nondeterministic. The same
slug-only matching is used to associate plans with the latest run and to hide a
static plan when a run exists.

Scaffolded projects are particularly likely to share names such as
`0001-todo-starter`. Every plan tab, plan-task tab, run lookup, collapse key,
and operation key should carry stable project identity. Tests should open two
folders with the same plan slug and assert that Start, Reset, rendering, and run
association remain folder-specific.

### 2.2 Reset does not execute the target shown in its confirmation

`reset_confirmation_for_context` captures the exact plan slug and
`task_list_path`. Confirming emits a parameterless `ResetRun`, and
`start_reset_active_run` recomputes context instead of consuming that snapshot
([`event.rs`](../../crates/makina/src/event.rs#L1267)).

The precedence rules differ: confirmation prefers the active plan context,
while `active_run_id` prefers the sidebar-selected run. A plan-A tab with run B
selected can therefore display a confirmation for A and reset B. Background
events can similarly change context while the modal is open.

The confirmed command must contain and validate the immutable target the user
approved. Operation guards should be keyed by the same project+plan identity.

### 2.3 `WorktreePolicy` fails open for missing or malformed paths

The policy checks paths only when `tool_call.extra["locations"]` exists and is
an array ([`permission.rs`](../../crates/makina-acp/src/permission.rs#L181)).
Missing, `null`, string/object values, empty arrays, elements without `path`,
and non-string paths all bypass validation. The request is then approved if an
`allow_once` option exists. A unit test explicitly requires missing locations
to be allowed ([`permission.rs`](../../crates/makina-acp/src/permission.rs#L496)).

The working-directory comparison is not containment: the session is launched
with that directory by construction. The subprocess inherits the parent
environment and receives no filesystem, process, or network sandbox
([`client.rs`](../../crates/makina-acp/src/client.rs#L759)). A pathless terminal
command can therefore access arbitrary host paths after automatic approval.

The current policy is useful for audit and convenience, but documentation
should not describe it as worktree isolation. If containment is required,
unknown/pathless requests must default-deny, every ACP path shape must be
validated, symlinks must be resolved safely, and the agent must run inside an
OS-level sandbox.

### 2.4 Concurrent persistence can commit an older snapshot last

Each driver snapshots the graph under its mutex, releases the lock, and then
persists independently ([`supervisor.rs`](../../crates/makina-core/src/actors/supervisor.rs#L263)).
`persist_graph` deliberately permits same-slug concurrent writes with
last-writer-wins behavior ([`persist.rs`](../../crates/makina-core/src/persist.rs#L144)).

Snapshot S1 can be taken before S2 but complete its rename after S2. The file
then moves backwards in task states, counters, and timestamps. There is no
unconditional final snapshot after all drivers drain, so stale state can remain
the crash-resume source of truth.

Persistence should be serialized per run, or guarded by a monotonic revision
and compare-and-swap rule. The scheduler should always write one final graph
after drivers finish. For power-loss durability, the temporary file and parent
directory should also be synchronized before and after rename.

### 2.5 Persisted graph identity is not bound to its requested plan

`OpenRun` derives a trusted slug from `TASKS.md` and loads that slug's artifact,
but it never verifies that the deserialized `TaskGraph.slug` equals the derived
slug. Graph validation checks task IDs and dependencies, not plan identity.
Subsequent persistence uses the graph's internal slug.

A malformed or edited artifact for plan A can therefore write over plan B's
artifact. Model-produced graphs have the same missing expected-slug check.
Expected project+slug identity should be passed into load/interpret validation
and used for all path construction, regardless of serialized content.

Corrupt or future-schema artifacts are also silently reinterpreted and then
overwritten. They should be quarantined or backed up and surfaced as an
explicit recovery/reset decision.

### 2.6 ACP idle termination can wait indefinitely

On idle timeout, the core awaits `session.terminate()` before returning the
timeout ([`agent_turn.rs`](../../crates/makina-core/src/actors/agent_turn.rs#L103)).
The ACP implementation first waits to reclaim a client held by the same worker
whose prompt stream is stalled. The existing out-of-band cancellation path is
not exposed by the generic `AgentSession` contract and is not invoked first.

As a result, the short idle cap can last until an outer wall-clock cancellation,
and cancellation can leave a detached worker owning the subprocess. Termination
should cancel or kill out of band before reclaiming the client, bound the
reclaim wait, and be covered by a silent-peer integration test.

## 3. Medium-severity findings

### 3.1 Start blocks the implemented TASKS-less generation flow

Core deliberately treats a missing plan-style `TASKS.md` as a request to
generate tasks from `SCOPE.md` and `ARCHITECTURE.md`
([`orchestrator.rs`](../../crates/makina-core/src/orchestrator.rs#L1431)). The
documented plan-discovery contract promises the same behavior
([`plan-discovery.md`](../plan-discovery.md#L37)).

The TUI Start path converts `has_tasks=false` into `PlanOpen::NoTasks`, reports
"author tasks first," and never calls `OpenRun`
([`event.rs`](../../crates/makina/src/event.rs#L557)). The UI should pass the
synthetic `plan.dir/TASKS.md` path to Core and let the existing generation path
run, with clear progress and failure states.

### 3.2 Closing a folder temporarily misindexes plan state

The close handler immediately compacts `opened_folders`, leaves
`plans_by_folder` untouched, and starts asynchronous rediscovery
([`event.rs`](../../crates/makina/src/event.rs#L509)). Rendering indexes the old
map using the newly compacted folder indices until the background result
replaces it.

Closing A from `[A, B]` can temporarily display and resolve A's plans beneath B.
The close operation should synchronously remove and rekey all folder-indexed UI
state, or use stable folder IDs instead of vector indices.

### 3.3 Disk-snapshot Start fallback remains incomplete for folder plans

The Start handler detects that a synthetic disk run ID is absent from the live
API and attempts to fall back to plan opening. Folder rendering, however, hides
a static plan whenever any run shares its slug, while run activation can only
open a plan tab through the legacy discovered-plan store. A focused synthetic
run can therefore fall through to `StartRun` with an unknown ID rather than
opening the folder plan.

Disk snapshots should retain canonical project and task-list identity so the
fallback does not depend on recovering a plan from slug-only UI state.

### 3.4 ACP exit diagnostics discard the actionable failure details

Transport EOF becomes `AgentExited` without child status or bounded stderr,
even though stderr is piped. The failed local run observed during this review
therefore recorded only "ACP agent exited unexpectedly". Capture command,
exit status, and a bounded stderr tail in terminal transport errors and persisted
failure reasons.

### 3.5 Status documentation is historical but presented as current

The README links `docs/trial/trial-findings.md` as the current source of
limitations and next steps. That trial document still says permission requests
are dropped and runtime persistence is absent, both of which have since been
implemented. It should be labeled as historical evidence, with unresolved
items moved to a current status or roadmap document.

## 4. Assessment of the current working-tree patch

The patch changes two Rust files and adds focused tests:

- `App::context_plan` now recognizes folder-scoped sidebar nodes.
- Active plan tabs search both the legacy and multi-folder plan stores.
- Unit tests cover a folder plan selected from a tab and from the sidebar.
- An async event test verifies `OpenRun` followed by `StartRun` for a folder
  plan through a `RecordingApi`.

This correctly repairs the user-visible "No run selected" regression for one
folder with one unique slug. Formatting, lint, and the focused tests pass.

The test seam omits the production properties that matter most:

- It has no repository root or worktree manager.
- It opens only one folder.
- It uses a unique slug.
- It invokes Start only once.
- It does not exercise Reset.
- It does not exercise disk-seeded runs.
- It calls the IO resolver directly rather than the complete palette/event
  redispatch path.

Before landing, coverage should include two real temporary Git repositories,
identical plan slugs, production `CoreApi` routing, repeated Start, confirmed
Reset targeting, closing/reindexing folders, and a disk-snapshot fallback.

## 6. What is working well

### 6.1 Clear crate and API boundaries

The split between `makina-core`, `makina-acp`, and the ratatui application is
clean. The TUI consumes an object-safe API; protocol details stay in the ACP
crate; orchestration and task-domain logic remain in Core. This makes fake API
and backend tests practical and keeps protocol replacement localized.

### 6.2 Strong orchestration foundation

The explicit FSM, dependency graph, deterministic gate chain, separate merge
serialization, worktree lifecycle, retry/review caps, and failure propagation
form a coherent system. The graph-lock discipline is well documented and
generally avoids awaiting while holding shared graph state.

### 6.3 Thoughtful process and worktree cleanup

ACP subprocesses use process groups and a descendant reaper. Worktree Git
metadata operations are serialized, removal is designed to be idempotent, and
base-branch recovery after merge conflict is treated as a load-bearing safety
property.

### 6.4 Persistence and audit are real, not aspirational

Runtime task graphs, recovery rules, run metadata, per-run logs, and permission
audit entries have concrete read/write paths and tests. The main persistence
gap is ordering under concurrency, not absence of implementation.

### 6.5 Broad deterministic coverage

The repository has extensive unit and integration coverage, in-memory ACP
transport tests, fake backends, fake APIs, and structural tests. The current
patch follows that pattern by adding regression coverage instead of relying on
manual TUI verification alone.

## 7. Maintainability observations

TUI state and behavior are now concentrated in very large modules:

- `crates/makina/src/app.rs`: approximately 13,500 lines
- `crates/makina/src/ui.rs`: approximately 13,200 lines
- `crates/makina/src/event.rs`: approximately 6,500 lines

Plan resolution is duplicated between app and rendering code, and slug-based
identity is reconstructed in several places. That duplication is directly
related to the folder-targeting defects. A typed `ProjectId`/`PlanId` and a
single project registry would remove entire classes of lookup ambiguity before
further multi-folder features are added.

worktree/build-cache hermeticity problem for an application that creates and
deletes worktrees. CI should perform a clean all-targets run, and local worktree
builds should avoid sharing target artifacts that embed source-root paths.

## 9. Recommended order of work

1. Introduce canonical project identity and route each run through
   project-scoped Core dependencies.
2. Enforce idempotent Open and one live run per project+plan; generation-guard
   scheduler finalization.
3. Carry project identity through tabs, runs, operations, disk snapshots, and
   folder-close state.
4. Make Reset consume the immutable target displayed in its confirmation.
5. Serialize/version persistence and write a final graph after scheduler drain.
6. Bind loaded/interpreted graph identity to the expected project+slug.
7. Decide whether `WorktreePolicy` is convenience or containment; document and
   implement the corresponding security boundary.
8. Make ACP cancellation out-of-band and preserve child exit diagnostics.
9. Restore the documented TASKS-less generation route.
10. Add two-repository integration coverage before declaring multi-folder
    execution complete.

---

## 10. Closing judgment

Makina's underlying design remains strong. The current risks are largely the
result of evolving a single-repository execution model into a multi-folder UI
without first making project identity a first-class core concept. Continuing to
patch slug lookups will increase ambiguity; introducing a canonical project/run
boundary will simplify the TUI and close the most serious safety gaps at once.

The present patch is a useful regression fix and a good diagnostic step, but
cross-repository routing and run exclusivity must be resolved before it is safe
to land as multi-folder Start support.
